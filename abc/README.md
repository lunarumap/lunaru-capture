# LUNARU Capture TEST 0.20 — A/B/C

Постоянный адрес для телефона: **https://lunarumap.github.io/lunaru-capture/abc/**. Вход в аккаунт не требуется. После обновления в шапке должна быть надпись TEST 0.20; достаточно обновить страницу, удалять данные сайта для обновления не нужно.

Отдельная страница `/abc/` для съёмки одной точки тремя способами. Корневая страница Capture и остальные модули не меняются. База — `LUNARU_Capture_TEST_0_13.html`, полученная с Google Drive (файл `1vQsG5OPGUe4LJJR6zBKVIqg3VNikKsYO`). Её код камеры, наведения и интерфейса сохранён в `base-013.js`; дополнения находятся в `abc.js`, `capture-support.js` и `abc.css`. Исходный HTML для сравнения — `tests/TEST-0.13-original.html`.

## Полевой сценарий

1. Открыть HTTPS-адрес `/abc/` в обычной вкладке Chrome на Redmi 9. Разрешить камеру и датчики; GPS нужен только при выборе соответствующего режима.
2. Создать объект, назвать точку. Весь тест остаётся в S01. Между A/B/C не менять физическую точку съёмки.
3. Выбрать A и открыть камеру. Проверить фактическое разрешение и источник фото. Начать, держать телефон вертикально; при отсутствии датчиков использовать ручную кнопку.
4. После A нажать «Завершить A → к B»: приложение предложит B, затем C. Незавершённый набор можно сохранить и доснять позже.
5. В C приложение сначала записывает и воспроизводит короткую пробу (она не включается в набор). Если режим не работает, проверяет меньший на том же объективе: до 1080p, затем до 720p. До начала прохода показаны проверенные размеры, fps и формат. Пауза/продолжение в открытой странице сохраняет один видеофайл. После остановки или перезапуска продолжение записывается отдельным файлом в набор C. Звук не записывается.
6. Перед закрытием страницы нажать «Прервать · доснять позже» для фото или «Сохранить видео · продолжить позже» для видео. Вернуться к наборам, нажать «▶ Проверить video…», проверить движение в ролике, затем скачать A, B, C по отдельности. Проверить ZIP в «Загрузках», затем подтвердить это кнопкой. Локальные исходники остаются в браузере.

Наборы:

| Набор | План |
| --- | --- |
| S01-A_photo_3rings | Прежняя сетка TEST 0.13: горизонт 12, верх 8, низ 8, зенит 2, надир 2 = 32 |
| S01-B_photo_zigzag | 12 секторов по 30°, по 3 наклона (±45°, 0°), направление чередуется; затем зенит 2 и надир 2 = 40 |
| S01-C_video_zigzag | Та же подсказка по 12 секторам, непрерывная запись; без извлечения кадров |

Завершение сетки не доказывает перекрытие или полноту сферы. Сшивка выполняется отдельно. Верхние/нижние кадры должны содержать детали соседнего ряда. Для PTGui распаковать фото A/B; видео C сначала требует отдельного этапа извлечения кадров, которого в этой версии нет.

## Данные и ограничения браузера

- IndexedDB `lunaru_capture_abc_v014`: `projects` — параметры, `files` — исходные фото, `chunks` — последовательные части исходной записи MediaRecorder. Имя базы и версия схемы не менялись: наборы TEST 0.14 продолжают открываться. Данные TEST 0.13 не затрагиваются.
- Фото и обновление счётчика сохраняются одной транзакцией. Счётчик растёт после успешного сохранения. Пересъёмка заменяет выбранный кадр только после записи нового; предыдущий Blob не удаляется автоматически.
- Запрос камеры: rear/environment, 3840×2160, 30 fps. После первого открытия закрепляются `deviceId` и доступный `zoom`; переключателей объектива/зума нет. Изменение доступных значений или потеря камеры приостанавливает фото на текущем кадре; для видео останавливается и сохраняется доступная запись.
- Фото: ImageCapture.takePhoto с максимальными доступными размерами из getPhotoCapabilities. Blob сохраняется без перекодирования; фактические размеры декодированного снимка записываются отдельно от запрошенных. Если API отсутствует, явно используется JPEG из видеопотока его исходного размера. При отказе takePhoto переход к кадру видео требует отдельного подтверждения.
- Видео: сначала контейнер MP4 без жёсткого профиля/уровня H.264 и без навязанного битрейта. При отказе — ограниченный перебор меньшего режима и WebM/настроек браузера. Одного isTypeSupported недостаточно: проба должна выдать файл, декодировать изображение и начать воспроизведение. Реальная настройка рекордера и результаты проб сохраняются в метаданных. Ни ресайза, ни транскодирования. Части записи сохраняются примерно раз в секунду, но браузер может задерживать события. Экран показывает подтверждённую сохранённую длительность. При скрытии страницы запись ставится на паузу.
- После аварийного закрытия доступны только уже записанные в IndexedDB части; последние ещё не сохранённые данные гарантировать нельзя. Такая запись помечается `interrupted`, а не завершённой; воспроизведение нужно проверить. Обычная остановка ждёт последнюю часть перед сообщением об успехе. Если событие stop не приходит за 5 секунд, уже записанные части сохраняются как interrupted; интерфейс разблокируется, успех не сообщается. Пустая неудачная попытка не выдаётся за видео.
- `capture.json` содержит время, фактические размеры, байты, MIME, метод, цель кадра, orientationModel и доступные yaw/pitch/сырые alpha/beta/gamma. Углы приблизительные, не геодезический азимут; gamma не выдаётся за калиброванный roll камеры.
- ZIP содержит оригинальные файлы, `capture.json`, `README.txt`. Локальная fflate 0.8.2 (MIT; лицензия рядом) записывает ZIP без сжатия, фото и видео не меняются.
- Браузер не сообщает сайту, закончилась ли загрузка в папку телефона. Поэтому отдельно показываются сохранение на устройстве, передача скачивания браузеру и подтверждение пользователя.
- Автоматического удаления данных нет. Очистка браузера, инкогнито, удаление данных сайта или нехватка места всё равно могут повлиять на хранилище. Встроенный запрос persistent storage снижает риск автоматической очистки, если браузер его разрешит.
- Для съёмки использовать одну вкладку. Установка PWA/на главный экран в этот тест не добавлялась.

## Обновление 0.20: результаты полевых проб

- В архивах iPhone 0.19 все 13 кадров A и 6 кадров B полностью чёрные. Видео читается. Точная причина приостановки камеры iOS не установлена; подтверждён пропуск проверки живого изображения перед сохранением. Полевая проверка новой версии на телефонах ещё нужна.
- До снимка проверяются live/enabled/muted, получение нового кадра и отсутствие полностью чёрного изображения. Декодируется и проверяется также полученный файл. Небольшая диагностическая выборка пикселей не меняет сохраняемое разрешение. Чёрный кадр, остановившийся поток или ошибка фото-API не увеличивают счётчик и не выбрасывают из съёмки: появляется восстановление камеры или явный выбор кадра видеопотока. Очень тёмная сцена/закрытый объектив также требуют проверки пользователем.
- Полноразмерный canvas освобождается после кодирования. Исходные JPEG и видео не уменьшаются. Диагностика последних 80 ошибок и строка браузера включаются в capture.json.
- Названия объекта/проекта и станции S01 меняются кнопкой на экране наборов или нажатием названия во время съёмки. Фото на время редактирования приостановлены; видео ставится на паузу и продолжается после закрытия окна. Идентификатор станции и исходники сохраняются; ZIP после переименования готовится заново с новыми метаданными.
- «Завершить A → к B» / «Завершить B → к C» сохраняет набор и переводит к следующему способу. «Прервать · доснять позже» сохраняет прогресс текущего фото-набора. В C отдельно обозначены непрерывная запись, таймер, пауза и сохранение видео.
- B/C могут начать с первой верхней цели без дополнительного наведения на горизонт. Для B/C применяется сглаживание около 160 мс; оптическая геометрия и сырые углы сохраняются. A сохраняет прежние 85 мс и допуски. Сглаживание не доказывает исправность датчика и не скрывает реальные изменения направления.
- Сетки A32/B40 сохранены. Вторые полюсные кадры явно названы 2/2; подсказка просит вернуться к горизонту и повернуться примерно на 90°. Поворот 90° не измеряется и не гарантируется приложением.
- При отказе системной передачи ZIP (Permission denied, в том числе на обоих Redmi) архив остаётся готовым: «Скачать готовый ZIP» скачивает тот же File без повторной сборки. Ошибка не обещает успешную отправку на Диск. Прямой Drive API всё ещё требует настройки OAuth; это не заменено системным меню.

## Обновление 0.19: все прошлые сеансы

- На главном экране кнопка «Удалить все прошлые сеансы» показывает число объектов и фактические байты исходников. После явного подтверждения очищает три хранилища A/B/C одной транзакцией. Отмена оставляет всё на месте. Во время съёмки/экспорта удаление запрещено.
- Не вызывает clear для localStorage или других баз и не удаляет скачанные ZIP/Google Drive. Старые данные отдельных нативных приложений или других браузеров не входят в эту очистку. После очистки можно создать новый объект и продолжить съёмку.
- Прямая загрузка на Google Drive ещё не подключена: у проекта нет настроенного OAuth client ID. Системная передача ZIP в 0.18 не является такой интеграцией. Требования к подключению описаны в GOOGLE-DRIVE-SETUP.md.

## Обновление 0.18: отправка ZIP и понятная очистка

- Для браузеров с файловым Web Share добавлена подготовка ZIP и отдельная кнопка «Поделиться ZIP → выбрать Google Диск». Второе нажатие вызывает системное меню непосредственно в пользовательском событии, после завершения сборки архива. Пользователь выбирает приложение и папку. LUNARU не может принудительно выбрать Google Диск или подтвердить завершение облачной загрузки.
- Отмена оставляет исходники и подготовленный файл для повторной попытки. После успешной передачи временная ссылка на File освобождается; исходники остаются в IndexedDB. Готовится один набор за раз. При отсутствии поддержки файлов/ZIP остаётся обычное скачивание и инструкция отправки через файловый менеджер. Никаких OAuth-токенов или ключей Google в приложении нет.
- На главном экране добавлена инструкция очистки, кнопка возврата названа «К списку объектов / очистка». Индивидуальное удаление объектов сохранено наряду с общей очисткой 0.19, оба действия — с подтверждением. Никакой автоматической очистки и удаления файлов на Google Drive.

- Прицел и геометрия 0.16 сохранены без изменений. Постоянный HTTPS-адрес `/abc/` не меняется, вход в аккаунт не нужен.

Это исправление воспроизводимых программных условий; точная причина конкретного отказа iPhone без его сообщения об ошибке не установлена.

ZIP в загрузках и копии на Drive не удаляются.

- Исходники не уменьшены. Например, 70 МБ на набор A × 100 станций — около 7 ГБ исходников, и скачанные ZIP займут дополнительное место. Очистка — только после проверки нужных копий.

## Наведение и датчики в 0.16

- Направление задней камеры теперь вычисляется по оптической оси −Z и всем трём углам W3C Z-X-Y, а не только alpha/beta. Неподвижный крестик совмещается с маленькой целью; кольцо показывает выдержку. Служебные сведения сокращены, предложение GPS не закрывает прицел, в помещении GPS не запрашивается.
- Существующие наборы с исходниками и сохранённым базовым углом продолжаются в прежней системе `legacy-013`: нельзя незаметно изменить их привязку. Для проверки нового наведения создайте новый объект. База IndexedDB не меняется и не очищается.
- Второй автоматический кадр одного полюса требует сначала вернуть камеру к горизонту. Это предотвращает два подряд одинаковых автокадра, но не доказывает перекрытие или смену точки зрения.
- Зависший takePhoto ограничен 6 секундами. При явном отказе запроса максимального размера разрешена одна попытка без параметров (4 секунды); переход на кадр видеопотока остаётся явным и требует подтверждения.
- Проверочное видео записывается 1,8 секунды и воспроизводится целиком. Измеряются декодированные кадры/длительность; менее 12 fps отклоняется до начала прохода. Последовательно проверяются исходный режим, 1920, 1280 и 854 px (последний до 15 fps), без смены камеры/зума. Выбранные параметры показываются до записи. Короткая проба не гарантирует отсутствия замедления при нагреве во время длинного прохода.
- Разрешение iOS запрашивается непосредственно при нажатии «Открыть камеру», до операций сохранения. При отсутствии данных есть отдельная кнопка повторного разрешения; во встроенном браузере датчики всё равно могут быть недоступны. Запись видео от датчиков не зависит.
- Прежние сетки A/B остаются. Только обработка наведения фото использует круговое сглаживание yaw (~85 мс), вход в цель ±7°, выход ±10° и выдержку 450 мс. Быстрое движение сбрасывает выдержку. Вблизи полюсов учитывается только наклон; сырые углы сохраняются отдельно.
- Это стабилизация показаний, а не доказательство точности датчиков или перекрытия кадров. На реальных телефонах нужно проверить ощущения от наведения.
- TEST 0.13 (`base-013.js`) и корневая страница не изменялись. Не очищайте данные сайта для обновления; новая версия подключает ресурсы с новым номером в URL.

## Проверки

Автоматические тесты: `tests/capture-abc.mjs` (полный A/B/C) и `tests/field-020.mjs` (чёрные кадры, muted при кодировании, восстановление, названия, отказ передачи ZIP, верхняя цель B/C). Требует Node, Playwright, fflate и Chromium. Сам запускает локальный HTTP-сервер (localhost разрешён как secure context), использует искусственную заднюю камеру 640×480 и реальный MediaRecorder. Логи явно отличают этот тест от реального Redmi 9.

```sh
npm install --prefix /tmp/lunaru-test playwright fflate
npx --prefix /tmp/lunaru-test playwright install chromium
PLAYWRIGHT_MODULE=/tmp/lunaru-test/node_modules/playwright \
FFLATE_MODULE=/tmp/lunaru-test/node_modules/fflate \
node tests/capture-abc.mjs
```

При уже установленном Chromium можно задать `CHROMIUM_PATH`. `TEST_BASE_URL` позволяет проверить опубликованный HTTPS-адрес тем же тестом, `TEST_OUTPUT` — каталог артефактов.

Обязательная проверка на физическом Redmi 9 перед полем, которую эмуляция не заменяет:

- HTTPS-адрес открывается в Chrome; задняя камера показывает изображение; разрешение видно до съёмки.
- Снять по 2–3 кадра A и B, записать 10–15 секунд C с паузой и продолжением. Проверить работу датчиков или ручного режима.
- Нажать остановку, перезагрузить страницу, открыть объект: фото, видео и прогресс сохранились. Доснять ещё кадр и часть видео.
- Скачать все три ZIP, распаковать на телефоне, открыть фото и видео; сверить размеры с `capture.json`. Затем загрузить ZIP на Google Drive.
- Только после этого выполнять полные проходы. Физическая проверка телефона не считается выполненной автоматическим браузерным тестом.
